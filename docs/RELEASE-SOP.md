# 发布纪律（SOP）

> 这份文件存在的原因很具体：2026-11-07 22:12 打出的一个 48 文件旧包，在发布目录里躺了 12 小时，而源码已经走到 52 文件。若发布环节直接取用，交付出去的包会缺 `references/error-codes.md`、两份 JSON Schema、`scripts/schema_check.py`，另有 6 个关键脚本是旧版——**正是那一轮修复要防的东西**。

## 一、发布目录只允许存在与当前冻结基线一致的包

`05-发布/` 下任何 `.zip` 都必须满足：

1. 解压后逐文件 md5 与最新 `04-QA/test-log-r*/00-freeze-r*-manifest.txt` **完全一致**（缺失 0、多余 0、内容差异 0）；
2. `sha256.txt` 里的 sha256、文件数、基线文件名三者与实际包一致。

不满足即视为污染，**先移出发布目录再谈其他**，不要在原地覆盖了事——覆盖会让人失去「上一版是什么」的线索。移出目标：`03-源码/_dev-logs/superseded/`，文件名带旧版本标识与 `SUPERSEDED`。

### 包只能由打包器产出，不接受手工 zip

r20 踩过这个坑：`validate_skill` 报了 2 个 error，官方 `package_skill.py` 因而拒绝出包，
但 `05-发布/` 里却有一份 54 文件、与冻结态逐字节一致的包——**它只能是绕过闸门手工压的**。
文件内容没错，错在这条纪律的反面：闸门存在的意义就是「不过就不许出包」，
绕过去之后，闸门再严也等于没有。

```
python <toolkit>/scripts/validate_skill.py --platform workbuddy --channel marketplace <技能目录>
python <toolkit>/scripts/package_skill.py  --platform workbuddy --channel marketplace <技能目录> <输出目录>
```

`<toolkit>` 指外部的 `skill-lifecycle-toolkit`，**不在发布包里**：本机位于
`~/.workbuddy/plugins/cache/experts/skill-lifecycle-studio/<版本>/skills/skill-lifecycle-toolkit/`。
换机器时要先确认这套工具在位，否则第三道闸根本无从执行——缺工具不等于通过。

`package_skill.py` 内置强制校验，**校验不过会 exit 1 且产物目录为空**。所以「打包器跑成功了」
本身就是「校验通过了」的证据；手工 zip 没有这层保证。


## 二、每次发布必须留下三样东西

| 物 | 作用 |
|---|---|
| `vector-ai-studio.zip` | 包本体 |
| `sha256.txt` | 文件数、字节数、包 sha256、对应基线文件名与其 sha256、客户可自行执行的校验步骤 |
| `发布说明.md` | 装什么、怎么装、已知问题（**含未修项的实测证据**） |

`sha256.txt` 不是给我看的，是给拿到包的人自证用的。所以里面必须写清「怎么验」，而不只是「验什么值」。

### 镜像仓库的目录结构（r61 记）

`repo-vector-ai-studio/` 不是「技能目录的镜像」，它自己是一层仓库：

```
repo-vector-ai-studio/
├ README.md  LICENSE  .gitattributes  .gitignore
├ docs/                ← 本目录的三份文档
└ vector-ai-studio/    ← 技能本体，95 个文件放这里
```

所以同步命令的目标是 `repo-vector-ai-studio\vector-ai-studio`，**不是仓库根**。
r61 我在仓库根上跑了 `robocopy /MIR`，`/MIR` 会删除目标端多余项，`.git`、`docs/`、
`LICENSE` 全被清掉。远端未受影响（按 `20a9834` 重新 clone 即恢复），但这类操作不可
回滚的前提是远端还在——若当时本地有未推送提交，就没了。

规则两条：一是 `/MIR` 只对 `vector-ai-studio\` 子目录用，且先用 `git status` 确认路径；
二是仓库根上只用 `git checkout` / `git clean` 恢复，不用 robocopy。

## 三、发布前的四道闸，缺一不可

```
selftest.py --fixtures    期望 63/63（不带 --fixtures 为 62/62；条数随断言增加，以实际清单为准）
run_fixtures.py           期望 24/24（r64 实测 24 passed / 0 failed）
validate_skill.py         期望 0 error / 0 warning
zip ↔ 冻结基线 双向 md5   期望缺失 0 / 多余 0 / 差异 0
```

四道闸里**最容易漏的是第四道**——前三道只证明源码好，不证明包里装的是那份源码。

## 四、旧包不删，只降级

`superseded/` 里的包保留原样，文件名标注它是什么版本、有多少文件、为什么被替换。删除会让人无法回答「客户手上那版到底是哪一版」，而这恰恰是交付纠纷里第一个要回答的问题。

## 五、基线不合格就不许发出

2026-11-08 曾建过一次 r7 基线，建完发现契约文档里两处反引号造成 `E-BROKEN-LINK`、校验不过，**没有发给 QA 就作废了**。

基线一旦发给下游，下游的结论就建立在一个可能不存在的状态上。宁可重算一次哈希，也不要让不合格的基线流出去。

## 六、为什么是这三条（不是道理，是发生过的三件事）

规则只写「要做什么」会退化成仪式——照做不知道为什么，第一次遇到例外就会破例。所以把来由写在这里。

### 6.1 开工先算哈希，才谈结论

**发生过的**：2026-11-07 23:55 我把 r5 基线发给 QA，23:56 又去补 `deliverable.schema.json`（新增了 `content_ops` 字段而 schema 没跟上）。33 秒的窗口，QA 开工时算出的当前态与基线差 1 个文件，它当场停下没有开工。更早一轮更糟：实现端在 QA 复测期间持续改源码，基线连续失效 3 次。

**所以**：顺序必须是「算哈希 → 宣布冻结 → 通知下游」，不能反过来。基线不是通知的一部分，是通知的前提。

### 6.2 结论必须能被第二路复核

**发生过的**：
- QA 用 `\brg\b` 类正则统计 PDF 颜色算子，报「未找到任何算子」；我按字节复核得到 `rg=3, RG=2`，它随后自查出两个错因（操作数个数按 CMYK 的 4 个写、数在了未解压字节上），主动撤回。
- 我写 `unverified` 文案时把「内容流是 rg」写成工具实测，实际工具从未统计过算子——事实为真，但不是工具测的。QA 指出这一点，我改成真去解压计数。

**所以**：一个结论只有一条证据路径时，它就是待验证的。同上，数据要能被第二个人用第二种方法算出同一个数。

### 6.3 发布目录只允许放与冻结态一致的包

**发生过的**：一个 48 文件的旧包（2026-11-07 22:12）在 `05-发布/` 躺了 12 小时，而源码已走到 52 文件。对照差集是 4 个文件缺失、6 个文件内容不同——缺的正是那轮新增的 JSON Schema、错误码表与校验器。

**所以**：前三道闸（selftest / fixtures / validate）全都只证明**源码**好，没有一道能证明**包里装的是那份源码**。第四道闸（zip ↔ 冻结基线双向 md5）是唯一能回答这个问题的检查，也是最容易省掉的那道。

### 6.4 一条推论

上述三条的共同点：**它们防的都不是「写错代码」，而是「结论与实际脱节」**。代码写错会被测试抓到；结论脱节不会——它看起来一切正常，直到有人拿它去交付。
